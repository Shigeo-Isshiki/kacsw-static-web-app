# 共通ライブラリの文書作成標準

このリポジトリのライブラリ仕様書は、利用者が現行APIを正しく使うためのリファレンスです。開発経緯・検証記録・保守手順とは役割を分けます。

## リファレンスの標準構成

各ライブラリの文書は、次の順序と見出しに統一します。

1. **概要・バージョン**：目的、対象環境、現行ソースのバージョン。配布確認済みかどうかを区別する。
2. **読み込み・依存関係**：配布URL、読み込み順、公開方式、必要な外部ライブラリ・サービスAPI。
3. **公開関数の目次**：機能別の一覧表。列は「関数名」「機能」「リファレンス」の順にし、各関数の解説へリンクする。
4. **関数リファレンス**：動作、引数の型・既定値、戻り値、未入力・不正入力・例外、副作用、利用例。共通のschema・options・結果型は同じ章にまとめ、各関数から参照できるようにする。
5. **制約・注意事項**：対象外、環境・通信・非同期の制約、安全性、既知の制限。必要な公式資料や詳細記録へリンクする。
6. **更新履歴・配布記録**：バージョン、記録日、主要な変更、コミットと配布確認状況。詳細ログは載せない。

既存の関数アンカーは可能な限り維持します。関数の追加時期ではなく機能で並べ、同じ説明を複数箇所へ重複掲載しません。複数のプラットフォーム（kintone・FormBridgeなど）向けのAPIが同一リファレンスにある場合、公開関数の目次と関数リファレンスをプラットフォームごとに分けます。複数プラットフォームに共通する機能は、各目次で機能順を揃えます。プラットフォーム固有の機能は、そのプラットフォームの目次にのみ記載します。

## バージョン・配布の記録

- 現行バージョンはJavaScript本体の先頭JSDocの `@version` と一致させます。機能変更時には両方を更新します。
- バージョンが未設定の現行ソースは、合意した基準版（今回は `1.0.0`）として記録します。過去の変更へ推測でバージョンを割り当てません。
- 過去の変更はGitで確認できる日付・内容・コミットを記録します。コミット日、初版作成日、配布日を混同しません。
- 「配布済み」は、デプロイや配布URLの内容を確認した場合だけ記載します。未確認の場合は明記します。
- 文書だけの変更で、ライブラリの機能バージョンを上げる必要はありません。

## リリース・通常配布確認の標準手順

この手順は特定ライブラリだけでなく、リポジトリ内のすべての共通ライブラリに適用します。ローカル検証・配布・配布内容の確認を別の段階として扱います。

1. **変更・バージョン・文書を揃える**：対象ライブラリの先頭JSDoc、リファレンス、更新履歴を更新します。ライブラリごとのバージョンを独立して管理し、リポジトリのpackageバージョンや他ライブラリの番号へ一律に合わせません。
2. **配布前に検証する**：変更に対応する既存テスト・静的チェックと文書検証を実行し、正確なコマンドと結果を記録します。未実行の検証は未実行と記載します。
3. **承認された変更を配布する**：[貢献ガイド](../CONTRIBUTING.md) のブランチ・PR手順とリポジトリの保護ルールに従ってコミット・プッシュ・マージします。本手順は、AIによる無断のコミット・プッシュ・本番反映や保護ルールのバイパスを許可するものではありません。
4. **配布対象のコミットを固定する**：本番反映されたコミットSHAを記録し、そのコミットのCI・デプロイ・配布パッケージ作成の結果を確認します。プッシュ成功や他コミットの成功を根拠にしません。
5. **通常配布URLを照合する**：デプロイ成功後、各リファレンスの通常URLからGETし、HTTP 200を確認します。候補版・圧縮版やローカル配信で代用しません。キャッシュの影響を抑えるため `Cache-Control: no-cache` を付け、取得ファイルを固定したコミットのソースとバイト単位で比較します。配布時に変換する構成では、そのコミットから生成された配布物と比較し、変換方法も記録します。JSDocのバージョンとSHA-256も確認します。
6. **確認範囲と証跡を残す**：ライブラリ更新時は変更対象すべて、リポジトリ全体の配布確認時は文書一覧の全ライブラリを照合します。対象名・通常URL・バージョン・確認日（タイムゾーンを含む）・対象コミット・HTTPステータス・一致結果・SHA-256・ワークフローへのリンクと結果を [通常配布確認記録](verification/library-distribution.md) に追記します。過去の記録は上書きせず保持します。
7. **確認済みの表記を更新する**：内容一致を確認できた対象だけ、概要を「現行ソース・確認済み通常配布版は **X.Y.Z** です。」とし、更新履歴に確認日・対象コミット・検証記録へのリンクを載せます。不一致・取得失敗・未確認の対象を成功扱いにせず、現行ソースと確認済み配布版の違い、失敗内容・未確認事項を明記します。
8. **確認記録を保存する**：確認後の文書変更も承認されたGit手順でコミット・プッシュし、そのコミットのワークフロー結果を確認します。記録の更新にソース変更が混在した場合は、新しい配布対象コミットに対して再照合します。

確認日は初版の公開日ではありません。CI成功・パッケージ作成成功・通常URLの内容一致・利用先の実画面動作は、それぞれ別の確認です。配布一致だけで、パッケージへの全対象の収録、利用先のブラウザーキャッシュ更新、機能・業務条件の実画面検証を保証しません。文書だけを更新してソースが変わらない場合は、既存の配布証跡を保持でき、全ライブラリの再照合や機能バージョンの変更は不要です。

## 本文に含めない内容

- 調査途中の仮説、試行錯誤、作業者への依頼文、将来の機能提案
- アプリごとの詳細検証表、一時診断コードの運用、CIログ、配布内容のハッシュ
- ソースを更新する具体的な保守手順、テスト用モックの詳細
- 「必要なら追記します」など対話の残りや、利用者への質問

判断の根拠が必要な記録は削除せず、[検証記録](verification/kviewer-custom-lib.md) や [保守・開発手順](maintenance/library-maintenance.md) へ分離します。これらの補助文書と本標準は、APIリファレンスの6章構成の対象外です。

## 確認済み・未確認の区別

公式仕様、自動テスト、利用者による実画面確認、未確認事項を区別します。特定アプリの観測を全ビュー・全環境へ一般化しません。APIの利用判断に必要な制約は本文に短く残し、詳細な確認条件やログは別文書へリンクします。

## 文書変更時の検証

章立て、関数目次、アンカー、相対ファイルリンク、コードフェンス、JSDocとのバージョン一致を確認し、`git diff --check` を実行します。文書のみの変更で動作テストは必須ではありませんが、実行例・API契約を変更した場合は該当する既存テストで確認します。
